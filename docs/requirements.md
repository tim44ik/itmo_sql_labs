# Требования к системе бронирования коворкинга

## 1. Роли пользователей

Роль хранится в `app_user.role` и ограничена `CHECK (role IN ('guest', 'employee', 'admin'))`.

| Роль (`role`) | Что делает | Доступ к данным (таблицы и колонки) |
|---|---|---|
| Гость | Просматривает список активных помещений и факт занятости интервалов. Не может создавать брони. | `SELECT room_id, code, capacity FROM room WHERE is_active = true`. `SELECT` из `booking` только по активным броням и без `user_id` — видит лишь `room_id` и `time_range`, чтобы понять, какие интервалы заняты. Нет доступа к `app_user` и `booking_event`. |
| Сотрудник / резидент | Ищет свободное помещение, создаёт и отменяет брони, видит брони и их историю. | `INSERT INTO booking` с `user_id = current_user`; `UPDATE booking SET status = 'cancelled' WHERE user_id = current_user AND status = 'active'`; `SELECT` своих `booking` (все колонки). Чужие брони — только факт занятости: `room_id`, `time_range` без `user_id`. `INSERT`/`SELECT` в `booking_event` только по своим `booking_id`. `SELECT` своей строки в `app_user`. Нет доступа к чужим `app_user`, к `UPDATE room`, к `UPDATE` чужих `booking`. |
| **Администратор** | Управляет помещениями и пользователями, отменяет любые брони, переводит в `no_show`, строит отчёты по загрузке. | Полный `SELECT`/`UPDATE` по `room` (включая `is_active`), `SELECT`/`UPDATE role` в `app_user`. Полный `SELECT`/`UPDATE booking.status` (в т.ч. `no_show` — сценарий 7). `SELECT` всех `booking_event`. Удаление `room`, `app_user`, `booking` запрещено на уровне БД (`ON DELETE RESTRICT`) — деактивация помещения только через `room.is_active = false`. |


## 2. Сценарии использования

### Сценарий 1. Просмотр доступных помещений
**Роль:** гость.  
**Шаги:**
1) Открывает список помещений.
2) Указывает дату и интервал.
3) Система показывает свободные помещения.  
**Результат:** гость видит только свободные помещения и не видит персональные данные.  
**Граничный случай:** если интервал некорректен (`начало >= конец`), система возвращает ошибку валидации.

### Сценарий 2. Создание брони
**Роль:** сотрудник.  
**Шаги:**
1) Выбирает помещение.
2) Выбирает интервал.
3) Подтверждает бронь.  
**Результат:** создаётся бронь со статусом `active`, если нет пересечения с активной бронью этого помещения.  
**Граничный случай:** при пересечении с существующей активной бронью СУБД отклоняет вставку ограничением `booking_no_overlap`.

### Сценарий 3. Отмена брони
**Роль:** сотрудник.  
**Шаги:**
1) Открывает бронь.
2) Нажимает «Отменить».
3) Система меняет статус на `cancelled`.  
**Результат:** бронь больше не блокирует интервал (`EXCLUDE`-ограничение учитывает только `status = 'active'`).  
**Граничный случай:** нельзя отменить бронь со статусом `completed` или `cancelled`; проверка выполняется в приложении или триггером.

### Сценарий 4. Двойная бронь одного помещения
**Роль:** сотрудник.  
**Шаги:**
1) Пользователь A бронирует помещение A101 с 10:00 до 11:00.
2) Пользователь B пытается забронировать A101 с 10:30 до 11:30.  
**Результат:** вторая бронь отклоняется ограничением `EXCLUDE USING gist (room_id WITH =, time_range WITH &&)`.  
**Граничный случай:** если первая бронь отменена (`status = 'cancelled'`), интервал снова доступен.

### Сценарий 5. Отмена после начала брони
**Роль:** сотрудник / администратор.  
**Шаги:**
1) Бронь уже началась (`now() >= lower(time_range)`).
2) Пользователь пытается отменить её как обычную.  
**Результат:** система запрещает отмену после начала без прав администратора.  
**Граничный случай:** администратор может принудительно закрыть бронь со статусом `no_show`.

### Сценарий 6. Отчёт по загрузке помещений
**Роль:** администратор.  
**Шаги:**
1) Выбирает период.
2) Запускает отчёт.
3) Система агрегирует количество броней и часы занятости по помещениям.  
**Результат:** отчёт по загрузке (OLAP-запрос по `booking`, `room`, `booking_event`).  
**Граничный случай:** если данных за период нет, отчёт возвращает пустой результат без ошибки.

### Сценарий 7. Просроченная / несостоявшаяся бронь
**Роль:** администратор.  
**Шаги:**
1) Бронь прошла, пользователь не пришёл.
2) Администратор переводит её в `no_show`.  
**Результат:** бронь не считается активной, интервал не блокируется.  
**Граничный случай:** нельзя перевести в `no_show` уже отменённую бронь.

## 3. Сущности и атрибуты

| Сущность | Атрибуты | Предполагаемый ключ | Тип ключа |
|---|---|---|---|
| `app_user` | `user_id`, `email`, `full_name`, `role`, `created_at` | `user_id` | суррогатный; `email` — естественный кандидат |
| `room` | `room_id`, `code`, `capacity`, `is_active` | `room_id` | суррогатный; `code` — естественный кандидат |
| `booking` | `booking_id`, `room_id`, `user_id`, `time_range`, `status`, `created_at` | `booking_id` | суррогатный |
| `booking_event` | `event_id`, `booking_id`, `event_type`, `payload`, `created_at` | `event_id` | суррогатный |

## 4. Связи и кардинальности

- `app_user 1:N booking` — один пользователь может иметь много броней; каждая бронь принадлежит ровно одному пользователю. Участие `booking` в связи обязательное.
- `room 1:N booking` — одно помещение может иметь много броней; каждая бронь относится ровно к одному помещению. Участие `booking` обязательное.
- `app_user M:N room` — фактически реализуется через `booking` как ассоциативную сущность с временным интервалом и статусом.
- `booking 1:N booking_event` — у одной брони много событий (`created`, `cancelled`, `completed`, `no_show`); каждое событие относится ровно к одной брони. Участие `booking_event` в связи обязательное.

## 5. Бизнес-правила и ограничения

1. В одном помещении не может быть двух активных броней с пересечением по времени. Проверяется `EXCLUDE USING gist (room_id WITH =, time_range WITH &&) WHERE (status = 'active')`.
2. Время начала брони должно быть меньше времени окончания: `lower(time_range) < upper(time_range)` (`CONSTRAINT booking_time_valid`).
3. Email пользователя уникален и должен содержать `@`: `UNIQUE`, `CHECK (position('@' in email) > 1)`.
4. Вместимость помещения должна быть положительной: `CHECK (capacity > 0)`.
5. Статус брони должен быть одним из: `active`, `cancelled`, `completed`, `no_show` (`CHECK (status IN (...))`).
6. Нельзя удалить помещение или пользователя, если на них есть брони: `ON DELETE RESTRICT` на `booking.room_id` и `booking.user_id`. Журнал `booking_event.booking_id` использует `ON DELETE CASCADE`.
7. Отменять можно только активную бронь; проверка выполняется в приложении или триггере.
8. Тип события журнала должен быть одним из: `created`, `cancelled`, `completed`, `no_show` (`CHECK (event_type IN (...))` в `booking_event`).

## 6. Профиль нагрузки

- **OLTP:** создание брони, проверка доступности, отмена брони, смена статуса, запись события журнала. Короткие транзакции, высокая требовательность к целостности.
- **OLAP:** отчёты по загрузке помещений, количеству броней, часам занятости, несостоявшимся броням, агрегаты по типам событий из `booking_event`.
- **Ожидаемые объёмы:** пользователи — тысячи; помещения — сотни; брони — сотни тысяч в год; события журнала — миллионы строк.

## 7. Нефункциональные требования

- **Доступность:** ориентировочно 99,5% для учебного проекта.
- **RPO:** до 15 минут; **RTO:** до 1 часа.
- **Безопасность:** сотрудник видит только свои брони; администратор — все; гость — только публичные данные. Для разграничения доступа в PostgreSQL используется RLS (`CREATE POLICY` + `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`).
- **Резервное копирование:** ежедневный дамп + WAL-архивирование в production-варианте.
